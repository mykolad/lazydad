# Sign-in for voting: design and plan

> The plan that replaced [#24](https://github.com/mykolad/lazydad/issues/24), agreed in October 2026. It ships as
> one pull request per issue (#68–#83, then the optional #85, in order), each safe to deploy on its own. Once they've all landed, `CLAUDE.md`
> is the reference and this file is the record of why.

## Goals

- **One vote per account and joke**, enforced by the server. A repeated or retried request changes nothing.
- **No personal data in the database.** No account ids, names, emails or avatars, no provider tokens, no users table.
- **Only signed-in readers vote.** Anonymous voting goes away, and its counts are reset to 0.
- **Free providers only:** Microsoft, Google, GitHub, Facebook and Telegram.

Left out on purpose:
- **X** charges per API call since February 2026 (no free tier for new developers).
- **Apple** needs a paid developer account.
- **Passkeys** would add no third party, but anyone can make unlimited passkeys, so they barely deduplicate.
- **Email links** would handle addresses and need a mail service.
- **Turnstile** doesn't deduplicate (it proves a browser, not an account), so it isn't part of the plan; #85 measures
  whether cheap accounts (Telegram's, above all) vote in bulk and adds it only where they do.

## What is stored

| Where | What | Personal? |
|---|---|---|
| `Votes` | `(JokeId, VoterKey)` key, `Value` (1 / -1), `UpdatedAt` | `VoterKey` is pseudonymous: HMAC-SHA256 of `<provider>:<account id>` keyed with the pepper |
| `Jokes.Up` / `Down` | the votes counted, kept for the feed's sort | no |
| `DataProtectionKeys` | ASP.NET Core's key ring, encrypted with a Key Vault key | no |
| Key Vault | `VoterKeyPepper` (and `…Staging`), the provider secrets, the Data Protection key | secrets |
| The browser | the sign-in cookie: the voter key and the provider's name, encrypted | the visitor's own |

- **The pepper** makes the key irreversible: GitHub and X account ids are public numbers, so a plain hash could be
  matched by hashing them all. It can't be changed or recreated: with a new one every voter is new, and their old
  votes stay counted but can no longer be changed or deleted.
- **One person, several providers** (GitHub and Google, say) is several voters. Linking them would mean storing a
  link between accounts, so it's accepted.

## Sign-in

- **Handlers:** ASP.NET Core's own, not Container Apps' built-in authentication, so sign-in runs locally and in the
  tests. OpenID Connect for Microsoft (`common`), Google and Telegram (`oauth.telegram.org`), scope `openid` only;
  `AspNet.Security.OAuth.GitHub` with no scopes; Facebook with `public_profile`. `SaveTokens = false`, and
  `OnTicketReceived` replaces the user with one holding only the voter key and the provider.
- **The cookie:** `__Host-lazydad`, HttpOnly, Secure, `SameSite=Lax`. A session cookie by default; **"Keep me signed
  in"** (unticked) makes it 90 days, renewed while used. EU guidance (WP29 Opinion 04/2012) exempts sign-in cookies
  from consent, but a sign-in kept across browser sessions only when the user chose it: hence the checkbox, and **no
  cookie banner**. Theme and language are preferences the visitor set (also exempt); telemetry sets no cookies. Adding
  analytics or tracking cookies would change that.
- **Both regions share one key ring** (`PersistKeysToDbContext`, `ProtectKeysWithAzureKeyVault`, one application
  name). Traffic Manager splits traffic 1:1, so a sign-in can start in West Europe and finish in Sweden Central.
  Staging has its own key ring and its own registrations at every provider.
- **Endpoints:** `GET /auth/signin/{provider}?returnUrl=` (local URLs only), `POST /auth/signout`,
  `GET /me` → `{signedIn, provider}`, `GET /me/votes?ids=…` → `{id: value}`, `DELETE /me/votes`, and
  `POST /auth/facebook/deletion` (Meta's data-deletion callback). All `private, no-store`, never in `JokeReadCache`.
- **`/privacy`** (UA/EN): who runs the site and a contact, the purpose (one vote per account) and its basis (the
  service the reader asked for), what's stored and for how long (until deleted), the reader's rights (their votes are
  shown; "Delete my votes"), and the services involved (Azure, Cloudflare, the chosen provider).
- **Locally:** a "dev" provider that exists only in `Development`, so local runs need no registrations.

## Voting

- `POST /jokes/{id}/vote {value}` (`[Authorize]`; `previous` goes away) sets the voter's vote: `VoteRepository`
  changes the row only if it still holds the vote it read, and the counts by the difference, in one transaction. A
  request that loses a race reads again, so the counts never move twice. Returns `{up, down, value}`.
- The page asks signed-out readers to sign in, remembers the clicked vote (`sessionStorage`) and sends it after the
  return. "My votes" come from `/me/votes`; `localStorage` no longer keeps votes.
- The rate limit counts per voter as well as per IP.
- **Reset:** migration `ResetAnonymousVotes` sets every `Up`/`Down` to 0 (`Down` is a no-op; backups are the way
  back). The old revision can count a few anonymous votes in the minute after the migration, so the scheduler's tick
  sets `Up`/`Down` to the sums from `Votes` where they differ, and counts each fix in a metric.

## A second database replica (West Europe)

The database's primary stays in Sweden Central; a readable copy in West Europe would serve that region's joke reads.
Nothing in this design changes, given these rules:
- **A failover group:** votes, the sign-in key ring, the scheduler lease and migrations use its read-write address;
  only joke reads (the feed, a joke, Top 3, similar jokes) may use the read-only one.
- **A reader can vote immediately after signing in, in either region.** Signing in writes nothing to the database (no
  users table), so nothing has to replicate first. The vote and `/me/votes` always use the read-write address, and the
  vote's answer carries the counts from its own transaction. Only other readers' counts may lag, by the read cache
  and the replica.
- **The key ring never reads from the replica.** On the very first start a key is created and used at once; read
  from a copy a few seconds behind, the other region couldn't open a cookie just issued. It's read about once a day.
- **The cost:** a vote from West Europe crosses to Sweden Central, a few round trips of ~20–30 ms each, the same
  as every request does today. The load test (#81) shows whether batching them is worth it.
- **A forced failover** loses a vote's row and its count together, since both are written in one transaction.

## Observability: how fast the real providers answer

The load test can't measure the real providers, so production does:
- `lazydad_signin_provider_duration_seconds{provider, outcome}`: the server's own calls to a provider during a sign-in
  (token exchange, user info), timed by a handler on each provider's back channel.
- A probe per provider every 15 minutes: exchanging a made-up code answers `invalid_grant` when the client id and
  secret are right and `invalid_client` when they aren't. It gives latency and availability without any sign-ins, and
  `/status` shows each provider as `valid`, `invalid` or `off`.
- `lazydad_signins_total{provider, outcome}` (started, completed, failed): completed / started is how many readers
  finish a sign-in. The time on the provider's own page is the reader's, so it isn't measured.
- Dashboard panels (p50/p95 per provider, sign-ins) and alerts (a provider `invalid`, a failing probe).
- Never logged: claims, account ids, voter keys. The `PersonalDataFilter` test also covers a cookie and a voter key.

## Tests

- **Unit (`TestServer`):** a fake provider through the handlers' `BackchannelHttpHandler`; the voter key is the only
  claim kept; voting is idempotent; signed out gets `401`; deleting adjusts the counts.
- **Smoke, without accounts:** each enabled provider redirects to its authorize URL with the right client id and an
  exact `redirect_uri`, and the provider answers without a mismatch error; `/status` shows every enabled provider
  `valid`.
- **Smoke, a real vote:** a sign-in path that accepts an Entra token for `api://lazydad-smoke` from the environment's
  deploy identity only (one object id), on the vote endpoints only, as one fixed voter. The runner votes +1, checks,
  and sets the vote back to 0. No passwords and nothing new in GitHub.
- **No test accounts for real logins:** providers block scripted logins (captchas, new-device checks, locks). A
  manual sign-in with each provider is on the runbook's checklist after any change to its registration.
- **Load test:** `tests/load/FakeIdentityProvider.cs` (a file-based app like `Seed.cs`) plays all five providers
  (OIDC discovery and signed id tokens; GitHub- and Facebook-shaped user endpoints) and approves at once, with a random
  account per sign-in. It runs as a second app in `lazydad-loadtest-rg`; `Auth:LoadTest:Authority` points every
  provider at it. The app refuses that setting unless the scheduler and the smoke path are off, and Deploy Environment
  fails if it exists on staging or production. `visitors.js`: about 30% sign in (spread over the five providers) and
  cast 2–5 votes (switching and removing some), fetching `/me/votes` per page; the rest read, a few voting signed out
  (`401`). With `replicas` > 1 a sign-in finishes on another replica, the cross-region case. `Seed.cs` seeds `Votes`.

### The owner's part (portal and Azure)

- Registrations, separately for production (`lazydad.fyi`) and staging: Microsoft (Entra app, all account types; a
  federated credential with `lazydad-production` instead of a secret where possible), Google (OAuth client, consent
  screen), GitHub (OAuth app), Facebook (privacy and deletion URLs; staging stays in development mode), Telegram (a bot
  from @BotFather per environment, its domain set).
- Key Vault, per environment: the pepper, the provider secrets, an RSA key for Data Protection; read access for each
  app's identity on its own entries only. Keep an offline copy of the pepper.
- An Entra app registration for `api://lazydad-smoke`; the deploy identities' object ids go into config.
- Cloudflare: let Meta's POST to `/auth/facebook/deletion` through the bot settings.
- Before sign-in-only voting (#82) ships: sign in once with each provider on staging, then on production.
